# GrowUrDhan — M2 Native Encrypted Vault and Database (As-Built)

**Date:** 2026-10-08  
**Implementation branch:** `GUD-Android-ChatGPT`  
**Build stage:** Native Android **development infrastructure**; not an authenticated consumer financial application or Play release.  
**Source reference:** `android-native/data/src/main/kotlin/in/growurdhan/data/vault/` and `android-native/core/model/`.  
**Immutable CASPARSER:** None of the parser source or existing Chaquopy invocation code has been modified.

## Architectural decision

The owner confirmed GrowUrDhan has **not been published** on Google Play, so a **new native database schema and encryption format** are authorized. No mandatory in-place import of unpublished development vaults. The React/Tauri vault remains separate and is not deleted or touched by the native M2 code.

- Database: native **SQLCipher Android** (Zetetic Community Edition), pinned to 4.17.0 to remain within verified Gradle/Android API 36 baseline.
- Data isolation: `Context.noBackupFilesDir/gud_native_v2/wealth.db`. Android backup is disabled and data extraction rules exclude sensitive app data.
- Key lifecycle: 256-bit random SQLCipher key generated by `SecureRandom`; authenticated AES-256-GCM wrapping under a non-exportable Android Keystore AES key. The `GUDKEY02` envelope is saved with Android `AtomicFile`. Raw DB-key bytes are zeroed after opening.
- Vault creation is **explicit**: `status()` never creates a vault; `openOrCreate()` does so only on user request. `ready` marker is written only after successful DB initialization/integrity checks. Any partial vault state (including a surviving wrapped key without the database, even when the ready marker is missing) is a fail-closed error, not a fresh reset.
- No network dependencies, personally identifiable telemetry or CAS statement data are used in M2.
- **Important:** Keystore-based at-rest encryption does **not** constitute user authentication. M2 deliberately has no app-level password or BiometricPrompt gate. The native APK must not be publicly distributed as a production finance vault until the authentication/session and backup UI gates are complete.

## Native schema (v1, new and intentionally incompatible with current WebView SQLite v9)

| Table | Meaning / invariants |
| --- | --- |
| `family_member` | Stable owner identifiers; at most one primary member |
| `custody_account` | Account belongs to a valid family member |
| `holding` | Enforced ownership and optional account ownership; nonnegative quantity/price as scaled 64-bit integers |
| `ledger_event` | Append-only accounting rows. Database **BEFORE UPDATE** and **BEFORE DELETE** triggers raise ABORT. Event-to-holding ownership is an FK. Optional unique source fingerprint prevents re-import of same transaction provenance |
| `snapshot_import` | Complete statement import, SHA-256 unique across the vault; member ownership |
| `statement_position` | Snapshot observation, not a BUY. Composite FK ensures member matches **both** source snapshot and holding |
| `vault_meta` | Native schema metadata namespace (no keys/tokens) |

All monetary amounts are **scaled INTEGER** at 10,000 subunits per INR; quantities have eight decimal places (scale 100,000,000), matching existing financial conventions. Kotlin domain uses checked `Long` arithmetic and `BigInteger` intermediate products for valuation; no `Double` is used in financial persistence. SQL foreign keys and integrity checks are enabled. All repository changes run under a serialized coroutine `Mutex` and an explicit SQLite transaction; failure triggers rollback.

### Statement import safety

- `complete=false` is rejected before any write.
- Empty or duplicate-holding snapshots are rejected pending explicit human review.
- Snapshot rows must refer to holdings owned by the same member as the snapshot.
- Repeated SHA-256 source returns `ALREADY_IMPORTED` with no extra rows.
- Statements older than the latest imported snapshot for the same member are rejected instead of silently superseding newer observations. Same-source re-import remains idempotent.
- Snapshots do **not** create ledger events; no holdings are auto-closed by M2.

## Portable backup format (`GUDNBACK` v1)

A **password-encrypted backup** is distinct from the device-only Keystore key. Export is generated entirely in volatile memory; no plaintext database or backup staging file is written to external storage.

- Magic: 8 ASCII bytes `GUDNBACK`
- Version: 1 byte
- PBKDF2 iteration count: 4-byte big-endian, fixed at 600,000
- Random salt: 16 bytes
- Random AES-GCM nonce: 12 bytes
- Ciphertext length: 4-byte big-endian
- Ciphertext: AES-256-GCM, authenticated with the entire header as associated data; 16-byte tag
- Key derivation: PBKDF2-HMAC-SHA256 with user-supplied backup passphrase (minimum 12 characters for new backups).
- Portable logical data: schema v1 JSON, all seven tables, integer values encoded as exact decimal strings.
- Bound: 32 MiB maximum plaintext backup and 100,000 rows maximum per table; native streaming backup will require a versioned upgrade if user data grows beyond that cap.
- Passwords and plaintext backup buffers are not persisted. Callers should clear mutable passphrase and returned buffer as soon as possible.

### Restore rule

Backup ciphertext is authenticated **before** any financial SQL transaction. Import runs **only into a new, empty native vault**. Any malformed record, FK violation, duplicate or database error aborts the transaction. No live vault data is wiped to accept a restore. The older `GUDVLT01` and `KOSHA1` formats are **not supported yet** in the M2 native codec; optionally implement one-time pre-release developer test-data import as an independent adapter, without changing the frozen parser or old backup definitions.

## Public API (native Kotlin)

`VaultRepository` in `android-native/domain/src/main/kotlin/in/growurdhan/domain/vault/VaultRepository.kt`:

- `status(): VaultStatus` — read-only lifecycle status, non-creating
- `openOrCreate(): VaultStatus`, `close()` — explicit Keystore and encrypted database lifecycle
- `createMember(FamilyMember)`, `createAccount(CustodyAccount)`, `createHolding(Holding)`
- `appendEvent(LedgerEvent)` — append-only
- `importSnapshot(StatementSnapshot): SnapshotResult` — atomic complete snapshot only
- `members()`, `holdings()`, `events()`, `health()`
- `exportEncryptedBackup(passphrase: CharArray): ByteArray`
- `restoreEncryptedBackup(passphrase: CharArray, ciphertext: ByteArray)` — empty-vault-only transactional restoration

The implementation `SqlCipherVaultRepository` is bound in Hilt to `VaultRepository` via `DefaultVaultRepository`. Compose `VaultScreen` explicitly requests creation and reports sanitized state from `VaultViewModel`; it does not display synthetic portfolio values or collect a vault login password.

## Known exclusions and future milestones

- No full financial UI, manual holding forms, bulk imports, reconciliation adapter or user authentication/biometric gating yet.
- No Play Billing, Gmail Sync, price feeds or filesystem-backed SAF backup picker yet.
- No compatibility import for older unpublished React/Tauri vaults or old locked `.kosha` backups.
- No encrypted key rotation or credential recovery from device loss without a separate password backup; losing Android Keystore key means the local DB cannot be decrypted.
- No staged Play release approval, independent mobile security test, crash/security telemetry assessment, native code shrinking smoke test or native library/16 KiB page-size validation yet.

**No legacy cleanup beyond obsolete branch test artifact has been performed.** React/Tauri and CASPARSER stay until replacement verification and explicit cleanup gate.

## M2 hardening follow-up (2026-10-08)

- The `status()` function now treats **any** partial vault artifact set as corruption/recovery-required, including a present wrapped-key file without a data file.
- `openOrCreate()` refuses to silently create a new DB when an existing wrapped key indicates lost or incomplete financial storage.
- `importSnapshot()` rejects an older statement after a newer import for the same owner; existing SHA idempotency remains unchanged.
- Two Android instrumentation regressions added: missing database/surviving key, and older snapshot rejection.
- The previous emulator failure was a **runner disk exhaustion** issue: SDK emulator needed 7,372.80 MB, 7,246.48 MB available, so no device tests ran. Reduced AVD allocation from 4096M to 2048M in workflow; actual new emulator result is pending CI.

**This is not a security attestation or proof of on-device encryption until instrumentation passes on an actual Android emulator/device.**
