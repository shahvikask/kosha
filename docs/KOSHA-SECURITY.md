# Kosha Security and Privacy Baseline

> **GrowUrDhan first market release — owner decision D57 (2026-10-26):** Financial vault backup/export, automated SAF backup, backup-file import and financial-data recovery/restore are **not available in the initial release**. They belong to the next upgrade. This note supersedes any older proposed screens, flows, requirements or tests in this document; those descriptions are retained only as legacy/future-upgrade references. Offline account-password recovery and standard CAS/CSV/PDF statement imports remain in scope. No backup or recovery must be advertised as active. See [base-release scope](implementation/BASE-RELEASE-SCOPE.md) and spec v1.3.

## Security objective

Kosha handles highly sensitive financial information. Privacy is a core product requirement, not an optional feature.

## Default data boundary

- Financial portfolio data remains on-device.
- CAS PDFs are processed locally whenever technically possible.
- Raw CAS documents are not uploaded by default.
- No cloud database is required for normal operation.
- No financial data is sent to analytics, crash reporting, AI services, or third parties without explicit user consent and a documented privacy decision.

## Sensitive information

PAN, demat identifiers, folio numbers, account identifiers, transaction records and CAS documents must be treated as sensitive financial data.

Raw PAN must not be placed in normal logs, telemetry, URLs, filenames generated by the application, or error messages.

PDF passwords/PAN values used to unlock a document should remain in memory only for the minimum processing period and should be discarded immediately after use. Persistent storage of such secrets requires a separate security design using platform secure storage.

## Local storage

The canonical local database should support encryption at rest, with SQLCipher or an equivalent platform-appropriate encrypted SQLite implementation as the target for production.

Encryption keys must not be hard-coded in source code, committed to Git, or stored as ordinary application preferences.

For Android, key-encryption material should be protected by the Android Keystore. Equivalent secure platform facilities should be used on other clients.

## Document lifecycle

Default lifecycle:

```text
User selects CAS PDF
        -> process locally
        -> validate/extract
        -> reconcile
        -> persist normalized data
        -> discard temporary document data
```

Persistent document retention should be an explicit user choice.

## Network boundary

External network requests must be classified before implementation. Market/reference-data requests may contain instrument identifiers but must not include unnecessary user portfolio context.

A future optional backup/sync feature must be separately designed and opt-in. It must not weaken the default device-only privacy promise.

## Logging

Logs must never contain:

- full PAN
- full CAS content
- PDF passwords
- complete transaction histories
- secrets or encryption keys
- unnecessary account identifiers

Use opaque local identifiers and redacted diagnostics.

## Import security

Imported PDFs are untrusted input. Parsers must be defensive against malformed files, unexpected encodings, huge page counts, decompression/resource exhaustion, malicious embedded content and parser exceptions.

PDF processing must not execute embedded scripts or external document actions.

## Privacy release gates

A release is blocked if testing demonstrates that sensitive portfolio data can unintentionally leave the device, is written to logs, is exposed through URLs, or is persisted without the documented protection level.

## Export

Exports are user-initiated. The application should clearly identify when an export contains sensitive financial data and should use platform share/storage mechanisms without silently uploading the export.
